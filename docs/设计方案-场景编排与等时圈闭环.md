# 设计方案：场景编排与等时圈闭环（任务卡 5）

> 架构出处：§7「等时圈结果的批量筛选：高德出多边形 → OB ST_Contains 批量过滤」、
> §3.1 闭环（约束 → 空间计算 → 检索 → 图层回流）、§5.1 场景 Skill 的 DAG 声明与双入口一致性。

## 1. 缺口（实读确认，三块板子已就位但没接成环）

| 已就位 | 出处 | 缺的那一环 |
|---|---|---|
| 意图槽位 `iso_minutes / travel_mode`（规则 + LLM 同契约，骑行归 driving） | 卡 4（`intent.py:67,209-223,455-469`） | `_constraints_node` 已转发进 `spec`（`graph.py:108-109`），但**下游没人用来筛候选** |
| 等时圈进图 | 卡 2（`graph.py:_isochrone_update`，在 `spatial_join` 体内） | 时机在 candidates **之后** → 候选筛选永远用不到它 |
| `multi_modal_search` 支持 `polygon_wkt`（MBR 预筛 + `ST_Contains` 复核，卡 1 冒烟 200 候选） | `query_builder.py:310` | 图里没人把等时圈的 `polygon_wkt` 喂给它 |
| 场景 Skill `run()`（MCP/CLI 直调） | §5.1 | 该路径**不产等时圈**，与 graph 路径产出不一致 |

## 2. 范围

做：candidates 节点体内前置等时圈并反哺检索；等时圈去重复用（硬要求，验收带计数断言）；
场景层 `build_plan` 声明 s4 + `run()` 编排对齐；四条单测 + 两条 TestClient 集成 + 真实冒烟。

不做：前端（卡 2/4 已完成 chips 与 l_iso 渲染）、骨架/边改动、`amap_gateway`/`spatial_router`
签名改动、多 worker 并发检查点压测。

## 3. 设计决定

**D1 骨架不动，反哺是 candidates 体内的迷你编排（卡 2 先例）。** 钉子测试
`set(nodes) - {__start__, __end__} == GRAPH_NODES` 必须继续绿。为可测性把
`_iso_request / _iso_matches / _isochrone_update` 从闭包提到**模块级函数**（签名带 `ctx`，
行为不变）——节点体只调它们，单测能直接打这三个纯函数，不必整个图跑。

**D2 只有「用户显式给了时间预算」才反哺检索；默认值只用于展示。** 判据只看
`spec.iso_minutes` 有没有值（不引入别的业务语义）：
- 有 → candidates 先算等时圈，把 `polygon_wkt`（**WGS84 版**，`ReachabilityOutput.polygon_wkt`）
  作为空间约束传入 `MultiModalSearchInput`，并按 `SpatialConstraint` 的**二选一契约**让位
  （`center/radius_m` 传 None，避免「圆 ∪ 面」双谓词互相打架）；等时圈产出顺手写进 state。
- 无 → 一个字节行为都不变（center+radius 检索，spatial_join 里照旧产出默认展示圈）。

**D3 用户画的框优先于等时圈。** 若同一轮里既有 `spec.polygon_wkt`（draw_polygon 手势）
又有 `iso_minutes`：几何约束用**手势框**（那是用户亲手圈的范围），等时圈仍算出来供展示，
并把 `iso_filter_skip="gesture_polygon"` 写进 state 说明为什么没用它。

**D4 去重按参数三元组判定，复用不发第二次请求。** `_iso_matches(已有产出, 请求)` 比
`mode / minutes / center`（经纬度容差 1e-6）。candidates 与 spatial_join 都走同一个
`_isochrone_update`：先查 `state["isochrone"]`，命中就**直接返回空更新**（不重复 emit tool 事件、
不重复调高德）。跨轮同理——同一 thread 的 state 会带上一轮的产出，参数没变就复用
（网关侧本来也有 600 s TTL，但少了往返与序列化）。

**D5 检索宁可宽不可空。** 反哺失败的两条路都回落 center+radius 并记原因：
`iso_filter_skip="no_polygon"`（reachability 没出多边形，例如有 key 但 distance 报错且无降级）
/ `"gesture_polygon"`（D3）。降级**正圆**算合法多边形，照常反哺（`degraded=True` 只是标注，
不改变「这就是 T 分钟可达范围」的语义）。`iso_filter_skip` 进 `BrainState` 也进 `tool.end`
载荷，前端与日志都能看到为什么这轮没用等时圈筛。

**D6 双入口一致（§5.1）：场景 Skill 声明 s4 并真编排。**
`build_plan` 增 `{"id":"s4_reachability","skill":"reachability","depends_on":["s2_spatial_join"]}`；
`SiteSelectionInput` 增 `iso_minutes/travel_mode`（默认 None）；`run()` 在 s2 之后、仅当
`iso_minutes` 有值时调 reachability，产出经
`render_spec(ctx, session_id, {"spec":…, "isochrone": dump})` 挂出 `l_iso`，
evidence 追加 `{"type":"amap","ref":"distance_matrix",…}`，`elapsed_ms` 计入。
说明一条差异（如实登记）：graph 路径的等时圈**参与检索**（D2 发生在 s1 之前），
场景直调路径里 s4 声明在 s2 之后、只补展示对齐——按卡片拍板执行，不擅自把 s1 往后挪。

**D7 测试免 key 反而更好用。** conftest 已强制 `GEOMIND_AMAP_KEY=""`，TestClient 链路里
reachability 走正圆降级：多边形是真的、`ST_Contains` 照跑，闭环能被测；需要在线采样形态的
用例自己注入 `MockTransport`。单元层用 stub 工具（计数 + 捕获入参），零 DB 零网络。

## 7. 风险

| 项 | 处置 |
|---|---|
| 正圆降级参与筛选会不会「圈太小漏候选」 | 降级半径 = T×名义速度（驾车 20 km/h），实测 15 min=5 km；候选口径本就在成都主城，量级够用。真实在线形态另有冒烟证据 |
| 一轮多调一次高德（candidates 阶段） | D4 去重 + 网关 TTL 600 s：同参数一轮只发一次 distance 请求，验收有计数断言 |
| 等时圈反哺后 radius 让位，`aggs`（网格聚合）还按 radius 统计 | 口径差异如实登记：聚合层是「检索半径内的网格」，与候选的「可达面」不完全同集合。要统一得给 spatial_join 也加面约束（超出本卡，登记为下一卡候选） |
| state 里上一轮的等时圈被复用 | 参数三元组一致才复用（中心/分钟/方式），不一致即重算，不会拿旧圈筛新范围 |

### 8.2 真实 key 冒烟（`python -c` 一次性脚本，同一会话两轮）

| 查询 | 圈（在线采样） | 命中半径档 | 候选 | 圈内/圈外 |
|---|---|---|---|---|
| 春熙路 + 步行 10 分钟 | `mode=walking minutes=10 degraded=False 采样=60` | 250 / 500 m | **2** | 2 / **0** |
| 春熙路 + 开车 15 分钟 | `mode=driving minutes=15 degraded=False 采样=60` | 500 / 1000 / 1500 m | **10** | 10 / **0** |

两组候选集不同（步行集是驾车集的真子集，交集 2），反哺 SQL 均含 `ST_Contains` + `BETWEEN`（MBR 预筛未破）
且**不含** `_ST_Dwithin`（圆约束确实让位）；`iso_filter_skip` 两轮都没有出现（= 真的用面约束筛的）。

### 8.3 与前几张卡的接缝（本次核对无误）

- 卡 4 槽位：`iso_minutes/travel_mode` 规则版实测能抽（"一刻钟"→15、"步行"→walking、骑行归 driving）；
  判据只看有无，图里没有第二份默认值——缺省值从 `ReachabilityInput.model_fields` 读（有单测钉住）。
- 卡 2 产出：`_isochrone_update` 从闭包提到模块级（可单测），节点集合与边一字未动；复用判据是
  `mode/minutes/center`（中心点容差 1e-6 ≈ 0.1 m）。
- 卡 1 契约：`SpatialConstraint` 的「圆 or 面二选一」在编译层本来就成立，反哺只是把选哪条交给约束。

### 8.4 偏差与如实登记

1. **`l_iso` 端点数据源不变**：反哺发生在 candidates 阶段，但端点仍读 `state["isochrone"]`——
   同一份产出，只是生产者提前了，无契约改动。
2. **场景直调路径的等时圈只补展示、不参与该路径的 s1 检索**（卡片拍板 4 的 DAG 就是 s4 依赖 s2）。
   要让直调也「先算圈再筛」，得把 s1 往后挪或改双阶段——超出本卡，登记待裁决。
3. **网格聚合口径仍是检索半径**：`aggs`（客流热力）按 center+radius 统计，而候选按可达面筛，
   两者集合不同（§7 已登记）。答辩时这处口径要主动说清，不要等被问。

### 8.5 遗留

- 「可达面优先」的评分/聚合统一（aggs 也地面约束）→ 需要 §4.3 依赖图重算配合，另卡。
- `iso_filter_skip` 目前只落 state 与 `tool.end` 载荷；chips 已能展示「等时圈 Nmin / 方式」（卡 4 做的），
  但**没展示"为什么这轮没用等时圈筛"**（手势框优先 / 无多边形回落）→ 卡 6 的约束编辑闭环里一起处理。
- 真实在线形态下步行圈半径只有 250–500 m（路网系数 + 实测限速），候选数会明显少于圆近似——
  这是事实而非缺陷，演示脚本里要提前说明。
