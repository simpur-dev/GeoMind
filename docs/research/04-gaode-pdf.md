## 3. AI 空间智能开放平台与四大 Skill

### 3.1 产品定位（P21，四大标签，原文关键句）

- **空间智能大模型**："内嵌'**人-时-地-事**'多维关联的空间知识体系，具备对现实世界**人地关系**的理解与推理能力，支撑深度区域洞察。"输入是"点位/区域"，输出是"客流/画像"。
- **全链路智能分析**："打破'人工收集、分析、决策'的低效闭环，实现**数据获取、特征提取、洞察生成与报告输出**的全流程智能化。"
- **高德时空数据**：依托"全域、高频、多维度的时空行为数据，覆盖**亿级用户真实出行轨迹**"。
- **AI 驱动新范式**："非传统 BI 或 SaaS 产品的 AI 套壳，而是**原生构建于大模型架构之上**的智能分析平台。"
- 总愿景："从'传统人工挖掘'到'AI 智能分析决策'"，定位与愿景 = "分析、决策、聊天解决"。

### 3.2 要解决的痛点（P22）

- **缺乏真实动态的空间认知**：依赖静态/局部数据难见全貌；多源信息割裂；数据更新滞后。
- **区域分析效率与一致性不足**：人工周期长、响应慢；分析逻辑非标、结论难复用；专业门槛高、一线难直接用。
- **策略效果缺乏客观验证依据**：缺少实施前后行为对比基线；难量化目标人群实际变化；效果评估依赖主观/间接指标。
- 趋势判断：Agentic AI 时代——"AI Agent 从辅助工具进化为能自主规划、分析和执行任务的智能体"；决策模式从"拍脑袋"转向"可量化、可验证"。

## 5. 空间智能方法论（重点，尽量保留原文）

### 5.1 出发点：旅行规划不是"生成攻略"（P36–P39）

- P36 原文："从一段文字，到一个可以执行的空间计划"；"旅行规划 = **选点 + 排序 + 分日 + 连线 + 校验 + 调整**"。一份可用规划要同时回答：去哪些地方？按什么顺序？每处停留多久？地点间怎样移动？时间/距离/体力是否可行？用户修改后怎样快速重排？
- **复杂性一·空间计算复杂（P37）**："从 A 到 B，和规划一整天，是两类问题"。行程 = **地点集合 + 访问顺序 + 时间分配 + 交通方式**——"任何一个变量变化，其他变量都可能需要重新计算"。难点不只是"把点连起来"，而是"决定选哪些点、怎样组合、怎样排序"。
- **复杂性二·数据与决策复杂（P38）**：数据要同时理解五类信息——地点事实（位置/类型/营业状态/服务设施）、空间关系（距离/可达性/顺路程度/聚集关系）、动态状态（交通/区域热度/时段差异）、体验语义（适合谁/氛围/偏好）、组合价值（互补/折返/重复）。数据流：`海量POI/路网/热力/时段信息 → 数据加工与空间特征 → 候选地点与候选组合 → 偏好匹配与路线约束 → 少量可解释方案`。"真正困难的是：从大量候选地点和数据维度中，选出少量适合当前用户、当前时间和当前路线的结果"。
- **复杂性三·产品交互复杂（P39）**：三组张力——个性化推荐 vs 需求激发、自动生成 vs 用户掌控、信息完整 vs 认知负担。产品要帮用户完成四件事：**看见、理解、比较、调整**。"不是在'全自动'和'全手动'之间二选一，而是提供一个逐步收敛的过程"。

### 5.2 三层能力（P40–P43，全书骨架）

P40 对应表（原文）：

| 场景困难 | 需要的核心能力 | 高德开放平台可提供的支撑 |
|---|---|---|
| 空间计算复杂 | **空间计算能力** | 路径、距离、可达性、多交通方式与几何关系计算 |
| 数据与决策复杂 | **空间数据能力** | 地点、路网、交通等事实数据，以及面向场景的数据加工与空间抽象 |
| 产品交互复杂 | **空间表达能力** | 地图渲染、点线面图层、热力、三维表达与交互联动 |

- 一句话概括（原文）："**算得出来、判断得更准、让用户看得懂并改得动**"。"空间计算→可执行；空间数据→可信；空间表达→可理解、可调整"。
- 原文强调："优秀的空间智能应用，是把三类能力组织成一个**完整闭环**，而不是只调用一个接口、只加一张地图。"

**（1）空间计算：把高德 API 变成 Agent 的空间工具（P41）**
- 原文："大模型负责理解与规划，空间工具负责计算与校验。"
- 执行链：① 用户自然语言 → ② 意图与约束结构化 → ③ 生成候选地点与方案 → ④ 空间工具计算距离/路径/可达性 → ⑤ 校验时间/顺序/交通方式 → ⑥ 局部调整并输出方案。
- 四条核心原则（原文逐条）：
  1. **不让模型猜距离**；
  2. **不让模型凭文字判断路线是否顺路**；
  3. **不把所有任务塞进一次生成**；
  4. **将计算结果保留为可复用的中间状态**。
- 执行模式："生成候选 → 调用工具计算 → 发现冲突 → 局部修正 → 再次校验（**循环，而不是单向流程**）"。
- 结构化状态 JSON 示例（原文照录）：
  ```json
  {
    "must_visit": ["地点A"],
    "optional": ["地点B", "地点C"],
    "daily_start": "09:30",
    "daily_end": "19:00",
    "walking_preference": "low",
    "transport_modes": ["walking", "transit", "taxi"]
  }
  ```

**（2）空间数据：从"返回数据"走向"理解空间"（P42，三层加工）**

| 层 | 名称（原文） | 内容（原文词表） |
|---|---|---|
| 3 | **决策特征层 Decision Feature** | 顺路程度、绕行成本、主题匹配、区域互补、拥挤风险、候选优先级 |
| 2 | **空间抽象层 Spatial Object** | 楼块、商圈、热点区域、可达范围、聚集关系、时段变化 |
| 1 | **基础事实层 Raw Data** | 地点、坐标、类别、道路、区域、交通关系 |

- 原文："数据的价值不只是被查询，而是被**加工成 Agent 能够理解和使用的决策变量**。"
- 加工要回答的问题（原文示例）：两个地点是否属于同一片区？加入路线后增加多少绕行？一组地点能否形成同一主题？某时段是否更适合某类地点？当前方案是否存在跨区往返？

**（3）空间表达：地图不是背景，而是决策界面（P43）**

| 层次 | 内容（原文） | 要点 |
|---|---|---|
| **几何表达** | 点、线、面、楼块、路线、范围 | "地点适合用点，行程适合用线，商圈、楼块和覆盖范围适合用面" |
| **数据表达** | 颜色、大小、密度、层级、时间变化、二维与三维关系 | "人群热力、候选评分和区域变化，不应全部塞进文字卡片" |
| **交互表达** | 选择、筛选、对比、联动、拖动、框选、时间切换与**局部重算** | "列表点击地图定位；地图框选列表筛选；调整路线及时展示变化" |

- 交互链路（原文）："**地图选择 ↔ 卡片高亮 ↔ 数据详情 ↔ 方案重算**"。
- 三维表达"应服务于问题本身：当高度、地形、建筑形态或城市地标关系会影响理解时，三维表达才真正有价值"。
- 目标（原文）："不是'更炫'，而是让用户用更低的认知成本，理解更复杂的空间信息。"

### 5.3 通用 7 步闭环（P44，可复用框架）

> 原文小标题："一个可复用的空间智能应用框架"。

| 步骤 | 名称 | 含义（原文） | 例子 |
|---|---|---|---|
| 1 | **理解意图** | "用户是谁？想解决什么问题？偏好与非目标是什么？" | "望京 SOHO 周边适合开奶茶店吗？" → 意图=奶茶店选址、用户=连锁品牌 |
| 2 | **建立约束** | "时间、空间范围、交通方式、预算、必选项与排除项" | 3 公里内、步行可达、白领密集、竞品少、预算/营业时间 |
| 3 | **生成候选** | "搜索地点、区域或其他空间对象，形成候选池" | 多边形/周边搜索 POI、楼块、商圈 |
| 4 | **空间计算** | "计算距离、路径、可达性、聚集关系与组合成本" | 5–20 分钟步行可达圈、绕行成本、顺路程度 |
| 5 | **数据决策** | "筛选、排序、分组、打分，并形成可解释的取舍" | 客流热力+竞品密度+居住配套三维叠加打分，输出 Top N |
| 6 | **地图表达** | "用点、线、面、热力、图层与交互展示结果" | 楼块按档位 3D 染色、热力图、候选卡片 |
| 7 | **用户反馈** | "支持增删、替换、拖动和局部重算，持续修正方案" | 用户删掉/拖动一个候选 → 局部重算 |

- **关键产物（原文照录）**："一份**持续更新的结构化空间状态**，而不是一段一次性生成的文本。"
- **闭环（原文）**："'7 用户反馈'重新指向'1 理解意图 / 2 建立约束'——用户的修改不是流程结束，而是新一轮计算的输入。"
- **结构化空间状态记录了什么（原文照录）**："用户想要什么；系统选择了什么；当前方案怎样计算得出；用户做过哪些调整；哪些部分需要重新计算。"
- 原文："这套框架不只适用于旅行规划，也适用于大量空间智能应用。"

## 6. 典型业务场景案例集

### 案例 A：零售连锁 / 量贩零食门店选址——赵一鸣（零食很忙）（P26）
- **背景**：20000+ 门店，60% 区县乡镇布局，年新增门店 3000+。
- **问题**：① 选址靠经验，固定半径划圈偏离真实步行可达；仅 4 类粗标签难建模；② 多数据源时效/口径不一。
- **分析流程/数据与空间计算**：
  - 【人口】百米网格人口 + 客流 → 输出网格常驻/工作人口与小时级客流（客群密度）；
  - 【场域】业态 POI 与 AOI 配套 → 业态点位分布 + 人群画像，识别商业空白、量化区域成熟度；
  - 【可达圈】实时步行辐射圈 → **5–20 分钟真实可达范围**，指导选址间距与覆盖分析；
  - 升级路径：4 标签→几十维建模；半径划圈→实时可达圈；多源混乱→统一数据口径。
- **产物/价值**：机会识别（客流热力+竞品密度+居住配套三维叠加）；分钟级铺位客群画像与新店-老店距离自动防冲突；模型复制到 1300+ 县。
- 定位金句："客户有规则、高德有数据、两者结合解决真实业务问题。"

### 案例 B：广告营销 / 投流人群分析——深演智能（P32）
- **问题**：哪些被曝光用户真正到店？到店人群画像？如何复用高价值人群？
- **流程**：客户上传 OAID/IDFA（IMEI）合规人群包 → 高德亿级位置数据底座 + **AOI 围栏 + 空间大模型算法**判定是否到访门店 → 输出"曝光∩到店"交集客流及画像（旅游偏好、是否有车等）。
- **产物**："广告曝光—线下到访"交叉分析闭环；"看了广告→真实到店→到店人群画像"全链路；品效合一、可量化可追溯。

### 案例 C：门店运营——某国产品牌手机（P33）
- **问题**：一店一策；原有依赖经验/静态行政区、营销一刀切、快闪店缺客流数据。
- **流程**：基于 LBS 的动态区域人群画像，**自定义地理围栏（如 3km 半径）** → 输出常驻人口、流动人口、消费能力、兴趣标签、职住特征。
- **产物**："位置+人群"双维洞察；门店潜力评估、快闪选址、本地化营销；API/离线数据灵活对接。

### 案例 D：两轮电动车行业选址&运营——雅迪/台铃/新日（P34）
- **方法论**：门店全生命周期"**建-管-优**"：
  - **建（增量布局）**：智能选址与网络优化——融合商圈模型、客群画像、商业配套与交通态势，解决"新店开在哪、多店排布不互斥"；
  - **管（风控准入）**：建店审核决策辅助——自动生成门店洞察报告，评估经销商提报店址可行性；
  - **优（提质增效）**：存量治理与客流转化——识别低效店，输出《清洗名单》与客流转归因，精准引流。
- **三个抓手**：全局可观（全国渠道作战地图空间底座，POI 门址+竞对分布一图统揽）；原生洞察（两轮出行专属客群模型：通勤热度/骑行偏好/生活聚集地）；自动报告（《门店洞察报告》《清洗诊断书》）。

### 案例 E：临街楼块分析（P45，方法论实时 Demo）
- **需求原文**："帮我找到适合开设社区咖啡店的临街楼块，并说明每个候选楼块的优势和风险。"
- **形态**：实时 Demo · 昆明主城 **16,926 楼块 × 3,539 路**——楼块按**临街档位 W1–W4 四档 3D 染色**，口径调整时四档实时重算。（图示：城市三维楼块模型，红/橙/黄/青绿按临街档位分级，路网叠加。）

### 案例 F：人群热力分析（P46，方法论实时 Demo）
- **需求原文**："看清全城 24 小时人群分布与日夜潮汐，找出稳定热点和变化最大的区域。"
- **形态**：网格柱状三维热力图，颜色/高度编码人群量，叠加自定义圈选区域（紫色多边形）。
- 金句（P46 底部）："**AI 擅长理解人的意图，地图擅长理解真实空间——把自然语言转化成可验证的空间决策，让用户看得懂、改得动。**"

### 附录能力：智能区块划分与派单（P27–P31）
- AOI/围栏数据层级（P27）：村/社区 → 乡镇/街道 → 自然街区 → 商圈 → 住宅小区 → 写字楼（在五级行政区划之外）。
- 三种分区：**行政分区**（五级行政区划绑定业务单元，例：社区→网点→服务商+单量）；**均衡分区**（按售点数量均衡切分，例：两街道 12/8 售点 → 两均衡区各 10）；**自定义分区**（多边形画区/沿路画区自动吸附，区域拆分合并）。
- 派单场景（P31）：订单地址/经纬度自动"**点查区块**"→ 归属区块 → 系统自动派单；支持导入 1–6 级行政区划、区块拓扑自由合并拆分。

## 7. 对 GeoMind 架构设计的启示（必须体现的模块/概念）

1. **核心产物 = 持续更新的结构化空间状态（State），不是一次性文本/报告**。架构必须有一等公民级的 `SpatialState` 对象，至少包含：must_visit/optional 候选集、约束（时间窗/交通方式/预算/偏好）、已选方案及其计算依据、用户操作历史、脏标记（哪些部分需重算）。对应 P41 JSON 与 P44 五条记录内容。
2. **7 步闭环必须作为 Agent 编排主循环**：理解意图→建立约束→生成候选→空间计算→数据决策→地图表达→用户反馈，且第 7 步回流第 1/2 步；执行模式是"生成→工具计算→冲突检测→局部修正→再校验"的**循环**，不是单向 pipeline。
3. **三层数据加工必须落表/落层**：基础事实层（POI/路网/行政/AOI 原始数据）→ 空间抽象层（楼块/商圈/可达范围/聚集关系/时段）→ 决策特征层（顺路程度/绕行成本/拥挤风险/候选优先级）。OceanBase 应承担"空间抽象层 + 决策特征层"的本地计算与存储（百米网格、楼块档位 W1–W4、可达圈预计算），这是区别于纯调 API 的大赛亮点。
4. **工具调用四条铁律要写进工具层设计**：不让模型猜距离（距离/路径/可达性一律走工具）、不让模型凭文字判断顺路、不一次性生成、中间状态持久化可复用。
5. **高德 API 与本地计算的边界建议**：
   - 调高德 API：地理/逆地理编码、POI 关键字/周边/多边形搜索、驾车/步行/骑行/公交路径规划、未来路径规划、距离测量、交通态势、天气、IP/硬件定位、坐标转换、Loca/地图渲染。
   - 本地 OceanBase 计算：候选池批量筛选与打分、百米网格人口/客流聚合、可达性（等时圈）批量计算、楼块档位 W1–W4 空间聚合、竞对密度/商业成熟度指标、点查区块（point-in-polygon）、用户状态维护与局部重算。
6. **空间计算工具化（Skill/MCP 化）**：把"距离/路径/可达性/几何关系/聚集关系/组合成本"封装为 Agent 可调用的原子 Skill，对应官方 Skill/MCP Server 形态；大模型只做意图理解与规划，不做几何计算。
7. **空间表达三件套**必须在前端/交互层体现：几何表达（点=地点、线=行程、面=商圈/可达圈/楼块）、数据表达（颜色/大小/高度/时间轴编码，而非文字卡片堆砌）、交互表达（地图↔卡片↔详情↔重算的联动、框选/拖动/时间切换触发局部重算）。
8. **业务域模型要内置**：人-时-地-事知识体系、职住距离、消费力分级、通勤/骑行偏好、AOI 楼块商圈层级、门店全生命周期"建-管-优"、广告曝光-到店归因（人群包∩围栏）等业务语言。
9. **可解释性**：数据决策步必须产出"可解释的取舍"（为什么选这个候选、优势/风险），案例中输出物普遍是《门店洞察报告》式结论 + 结构化数据（HTML/Excel/JSON 多模态）。
10. **规模感参考**：实时 Demo 处理 16,926 楼块 × 3,539 路并支持 W1–W4 口径实时重算——架构要验证"大规模空间对象 + 参数变更触发局部重算"的性能。
