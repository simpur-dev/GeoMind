# GeoMind 10 万级索引压测报告

> 日期：2026-10-15 ｜ 环境：Docker 容器 `seekdb`（`5.7.25-OceanBase seekdb-v1.4.0.0` / OceanBase 4.3.5.3）
> 数据：成都主城 10 万行 POI（五模齐备），其中 **10 万行 × VECTOR(1024)**，另 100 个网格面
> 关联：《GeoMind架构设计文档.md》§6、《SeekDB环境实测报告.md》、《开发进度.md》
> 复现脚本：`scripts/bench/`（生成器 + DDL + 压测模板，见 §7）

---

## 1. 一句话结论

**空间索引（SPATIAL KEY）在 SeekDB V1.4 上完全不参与查询计划——空间过滤恒为 O(N) 全表扫描；而向量（HNSW）、标量、全文、以及三模/四模混合检索全部命中索引。**

好消息是找到了两个**已在 10 万级实测验证**的绕行方案，把最坏场景从 **5.56 秒压到 20 毫秒（278×）**，且绕行后的 SQL 仍然把空间计算留在数据库内核里完成（不违反「空间计算不下放 LLM」铁律）。

| 核心指标 | 原方案 | 绕行方案 | 加速 |
|---|---|---|---|
| 圈选（1.1 km） | 61–92 ms（全扫） | **<1 ms**（MBR 预筛走 B-tree） | **>60×** |
| KNN 最近邻 top10 | 71–81 ms（全扫排序） | **10 ms**（MBR 预筛后排序） | **7×** |
| 网格归属聚合（100 网格 × 10 万点） | **5559 ms**（NL JOIN + 全扫） | **20 ms**（冗余 grid_id + 普通索引） | **278×** |
| 向量 ANN top10（10 万 × 1024 维） | 精确 123 ms | 近似 **61 ms**（HNSW） | **2×**（召回 10/10 一致） |

## 4. 结果明细

### 4.1 空间检索（10 万行，SPATIAL KEY 存在但不命中）

| 查询 | 命中行数 | 实测耗时 | 执行计划 |
|---|---|---|---|
| `COUNT(*)` 全表 | 100,000 | 3–35 ms | TABLE FULL SCAN |
| `_ST_Dwithin` 0.002°（~220 m） | 7 | **121 ms** | TABLE FULL SCAN（EST 3.04 s / EST.ROWS 25000） |
| `_ST_Dwithin` 0.01°（~1.1 km） | 157 | **61–92 ms** | TABLE FULL SCAN |
| `_ST_Dwithin` 0.05°（~5.5 km） | 3,874 | **63 ms** | TABLE FULL SCAN |
| `ST_Contains`（常量大框） | 8,954 | **61 ms** | TABLE FULL SCAN |
| `ST_Intersects` / `ST_Within`（常量多边形） | — | 同量级 | TABLE FULL SCAN |
| `ST_Intersects(location, ST_Buffer(pt, r))` | — | 同量级 | TABLE FULL SCAN |
| `ST_Distance_Sphere(location, pt) < 1000` | — | 同量级 | TABLE FULL SCAN（EST.ROWS 33333） |
| KNN 全表距离排序 `ORDER BY ST_Distance_Sphere LIMIT 10` | — | **71–81 ms** | 全扫 + top-n |
| 空间圈选 + `GROUP BY category` | 20 组 | **71 ms** | 全扫 + 聚合 |
| **空间连接** `JOIN grid ON ST_Contains(cell, location) GROUP BY` | 100 组 | **5559 ms** | MERGE GROUP BY ← NESTED-LOOP JOIN ← MATERIAL（POI 全表物化）+ 网格全扫 |

**排除的干扰因素（都试过，结论不变）**：

| 尝试 | 结果 |
|---|---|
| `ANALYZE TABLE` 收集统计信息 | 计划不变，仍全扫（选择性恒按 25% 估） |
| `/*+ INDEX(t_bench_poi idx_loc) */` 强制提示 | **提示被忽略**，仍全扫 |
| `MBRContains` / MBR 系列函数 | **函数不存在**（ERROR 1305） |
| 换谓词形式（Contains / Within / Intersects / Buffer / Distance） | 全部全扫 |

→ 即 **优化器根本没有为空间谓词生成索引路径**，不是代价估算选错的问题。

### 4.2 绕行方案实测（均已跑通）

| 查询 | 命中 | 耗时 | 执行计划 |
|---|---|---|---|
| MBR 预筛 + 精确复核：`lon BETWEEN … AND lat BETWEEN … AND _ST_Dwithin(…)` | 157 | **<1 ms** | `TABLE RANGE SCAN t_bench_poi(idx_bbox)`，range(104.0568,30.6498 ; 104.0768,30.6698) |
| KNN + MBR 预筛 | 10 | **10 ms** | `TABLE RANGE SCAN(idx_bbox)` + top-n |
| 冗余列 JOIN：`JOIN … ON p.grid_id = g.grid_id` | 100 组 | **20 ms** | `TABLE RANGE SCAN p(idx_grid)`，`nl_params_([g.grid_id])`、`use_batch=true` |

计划对比（EST.TIME）：空间连接 194,181,878 μs → 冗余列 JOIN **2,132 μs**。

### 4.3 标量 / 全文 / JSON

| 查询 | 命中 | 耗时 | 索引 |
|---|---|---|---|
| `category=0 AND status=1` | 4,495 | **10 ms** | ✅ `TABLE RANGE SCAN idx_cat` |
| `MATCH(name) AGAINST('咖啡')` | 5,000 | **10 ms** | ✅ `TEXT RETRIEVAL SCAN idx_ft`（ngram，pushdown_match_filter） |
| `JSON_EXTRACT(props,'$.price') >= 200` | 35,239 | **91 ms** | ❌ 全扫（JSON 无索引路径，与预期一致） |
| `GROUP BY category` 全表 | 20 组 | **41 ms** | 全扫 + 聚合 |

### 4.4 向量检索（10 万 × 1024 维）

| 查询 | 耗时 | 执行计划 |
|---|---|---|
| ANN top10（`APPROXIMATE`，**热态**） | **61 ms** | ✅ `VECTOR INDEX SCAN t_bench_poi(idx_emb)` |
| ANN top10（**冷启动首次**） | 670 ms | 同上（索引未预热） |
| 精确 top10（无 `APPROXIMATE`，热态） | **123 ms** | 全扫 + top-n |
| 标量过滤 + ANN（`category=0`） | 143 ms | ✅ `VECTOR INDEX ADAPTIVE SCAN (PRE-FILTER)` |
| 2 万向量时 ANN / 精确 | 51 ms / 51 ms | 规模太小，差异不显著 |

**召回验证**：近似 top10 与精确 top10 的 id 与距离**逐条完全一致**（10/10，三轮重复均一致），本数据中 HNSW 无召回损失。

### 4.5 混合检索（核心叙事）

| 查询 | 耗时 | 执行计划 |
|---|---|---|
| 三模：空间 + 标量 + 语义（无 MBR） | **50 ms** | ✅ `VECTOR INDEX ADAPTIVE SCAN (PRE-FILTER)`，驱动索引 `idx_cat`，空间谓词作 filter 后置 |
| 四模：MBR + 标量 + 空间 + 语义 | **20 ms** | ✅ `VECTOR INDEX ADAPTIVE SCAN (PRE-FILTER)`，**驱动索引换成 `idx_bbox`**（range 104.0468–104.0868），EST.ROWS 1161 |

四模混合这条 SQL 就是参赛叙事的落地形态：

```sql
SELECT id, name,
       ROUND(ST_Distance_Sphere(location, ST_GeomFromText('POINT(104.0668 30.6598)')),0) AS dist_m,
       ROUND(cosine_distance(emb, '<1024维查询向量>'),4) AS sem
FROM t_bench_poi
WHERE lon BETWEEN 104.0468 AND 104.0868          -- ① MBR 预筛（走 idx_bbox）
  AND lat BETWEEN 30.6398 AND 30.6798
  AND category=0 AND status=1 AND rating>=4.0     -- ② 标量过滤
  AND _ST_Dwithin(location, ST_GeomFromText('POINT(104.0668 30.6598)'), 0.02)  -- ③ 精确空间复核
ORDER BY cosine_distance(emb, '<查询向量>') APPROXIMATE  -- ④ 语义召回（HNSW）
LIMIT 10;
```

## 5. 三条硬结论

1. **【坏消息·已坐实】SPATIAL INDEX 在 V1.4 是"装饰品"**
   7 种谓词形式 + 强制 hint 全部走全表扫描，`MBR*` 系列函数根本不存在。后果：空间过滤是 O(N)，10 万行约 60–90 ms 尚可接受，但**随数据量线性劣化**，1000 万行将到 6–9 秒量级。答辩时不能宣称"空间索引加速"，必须如实说明并给出绕行方案。

2. **【好消息·核心叙事成立】向量 / 标量 / 全文 / 混合全部命中索引**
   - HNSW 10 万级稳定 2× 于精确计算，召回 100%；
   - 三模混合走 `VECTOR INDEX ADAPTIVE SCAN (PRE-FILTER)`——**"一条 SQL 完成空间圈选 + 业务条件 + 语义召回"这个核心卖点在 10 万级实测成立**；
   - 加了 MBR 预筛后优化器会把驱动索引从 `idx_cat` 换成 `idx_bbox`，四模混合反而更快（50 ms → 20 ms）。

3. **【应对·已量化】两个绕行方案，且都不违反架构铁律**
   - **方案 A · MBR 预筛**：POI 表冗余 `lon/lat` 两列 + 复合 B-tree `KEY(lon,lat)`，空间查询写成「MBR 粗筛 + 精确 ST 复核」两段式。圈选 **>60×**、KNN **7×**。
   - **方案 B · 冗余归属列**：网格/行政区归属预计算成 `grid_id`（或 `adcode`）冗余列 + 普通索引，JOIN 走等值索引而非 `ST_Contains`。**278×**（5559 ms → 20 ms）。回填可全在库内完成（`ST_X`/`ST_Y` + 算术，10 万行 906 ms），无需应用层搬运。
   - 两者都**仍由数据库计算**，空间逻辑没有下放到应用或 LLM，只换了索引路径。

## 6. 对架构设计的修改要求

| 位置 | 修改 |
|---|---|
| 《架构设计文档》§6.3 生产 DDL | POI 表必须增加 `lon DOUBLE` / `lat DOUBLE` + `KEY idx_bbox(lon,lat)`；网格/区域统计场景增加归属冗余列 + 普通索引 |
| 《架构设计文档》§6.4 查询模板 | 空间过滤一律固化为「MBR 预筛 + 精确 `ST_*` 复核」两段式；禁止裸写 `_ST_Dwithin` / `ST_Contains` 作为唯一过滤条件 |
| SPATIAL KEY 去留 | **建议保留**（成本仅存储，且内核后续可能支持），但查询路径**不得依赖**它；文档中注明当前版本不参与计划 |
| 《实测报告》能力矩阵 | 空间索引行由"待验证"改为"**已验证：不命中**"，并链接本报告 |
| 下推边界 | 不变——绕行方案仍在库内完成，铁律「空间计算不下放 LLM」不受影响 |
