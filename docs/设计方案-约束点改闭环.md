# 设计方案：约束点改闭环（任务卡 6）

> 架构出处：§9.2 左栏「约束 chips（租金/半径/时段，可直接点改）」、§9.3 feedback 契约
> 的 `constraint_edit` 类型、§2.2 L2 约束建模器（spec 是唯一的约束载体）、
> §3.1 闭环「约束变更 → 局部重算 → 图层回流」、§9.6 职责边界表（裁决全在后端）。

## 1. 缺口（实读确认）

| 已就位 | 出处 | 缺的那一环 |
|---|---|---|
| `FeedbackEvent.type` 枚举含 `constraint_edit` | `map_spec.py:92-93` | 端点 `feedback()` 无该分支 → 落到底部 `HTTPException(400, "未知 feedback 类型")` |
| `draw_polygon` 已有「带 query 重跑一轮 + 返回 ChatOut」先例 | `routes.py:214-222` | 约束变更没有同等通道：只能重新打字，改不动单个约束 |
| chips 展示完整（含半径/评分/等时圈/方式） | `ChatPanel.vue:15-28` | 只读 `<span>`，点不动（注释里明写「暂不开放编辑」） |
| `_constraints_node` 组装 spec（十键） | `graph.py:93-115` | 外部没有任何办法把「用户改过的值」注进 spec——意图槽位是唯一来源 |

## 2. 范围

做：`ConstraintOverrides` 校验模型（四项白名单）；`BrainState.spec_overrides` 与
`run_query/resume_query` 的关键字参数；`feedback` 端点 `constraint_edit` 分支；
前端 chips 原地点改 + `editConstraint`；四条后端用例 + HITL 回归。

不做：keywords / center / 类目 / `time_bucket` 的点改（理由见 D1）；新 SSE 事件类型；
`FeedbackEvent` 契约改动；7 节点骨架与边；`IntentResult`；UI 组件库。

## 3. 设计决定

**D1 白名单只有四项，且每一项都有「为什么不开放」的话要说。**

| 可点改 | 区间 | 依据 |
|---|---|---|
| `radius_m` | 100 – 50 000（整数米） | 检索半径是「范围」这一维最直接的旋钮；上界比 `MultiModalSearchInput` 的 `le=100_000` **更严**——50 km 已是城市尺度，chip 上给到 100 km 只会产出一屏无意义候选。取 int 与意图槽位产出的类型同型（否则「改回原值」会让 `1500` 变 `1500.0`，破坏逐字节一致，实测抓到过） |
| `min_rating` | 0 – 5 | 与 `ScalarConstraint`/`MultiModalSearchInput` 的 `ge=0, le=5` 同界（库内 `rating` 值域） |
| `iso_minutes` | 1 – 120 | 直接取 `ReachabilityInput.minutes` 的 `ge=1, le=120`，不写第二份口径 |
| `travel_mode` | `walking` \| `driving` | 复用 `IsoMode` 类型（高德距离测量无骑行档，卡 1 实测） |

不开放：`keywords`（自由词进 ngram 全文极易 0 命中，`intent.py` 实测踩过 attrs 词不在 POI 名里）、
`center`（改中心本质是地图手势，`draw_polygon`/`range_drag` 已有）、类目（改类目等价于重新提问，
走 chat 更诚实）、`time_bucket`（客流时段不是「范围/门槛」类可调旋钮，chip 上也没有编辑语义）。
白名单外的键一律 **422**，且 422 之前不碰图——状态必然不变。

**D2 生效语义 = 「按这组约束重算一次」，不是「就地改 state」。**
payload `{"changes": {…}, "query": <lastQuery>}`；端点校验后经
`run_query(query, ctx, thread_id=sid, spec_overrides=changes)` 重跑整轮，返回与 chat
同形的 `ChatOut`。这样：候选/聚合/决策/图层/chips 一次全刷新，且复用了 `draw_polygon`
已经验证过的通路（SSE 事件流同款，无需新事件类型）。把 spec 就地改掉再指望下游重算，
需要新节点或图内失效协议——那是骨架改动，违反 §5.6。
「一次」要有牙齿：`run_query` **每轮都写**这个通道（不传即 `None`），所以下一次新提问
按意图重新装配，不会悄悄继承上一轮点过的 3000 m——与 `gesture` 完全同规约
（`spec_overrides` 与手势都是「本轮输入」，不是会话常驻状态）。集成用例把这条钉住了。

**D3 `spec_overrides` 在 `_constraints_node` 组装 spec 之后应用。**
节点先把意图槽位装配成十键 spec（缺省口径仍由这里定），再按
`overrides.keys() & ConstraintOverrides.model_fields.keys() & spec.keys()` 覆盖同名键。
三路交集 = 白名单只在 `ConstraintOverrides` 定义一处、图里不写第二份名单，而绕过端点
塞进来的陌生键（含 `center`/`keywords`/`time_bucket` 这些**确实在 spec 里**的键）
也污染不了约束——它们不在模型字段里，就进不了循环。`spec_overrides` 缺省 `None`
→ 循环零次 → 逐字节走现状。
`run_query` 只是多一个关键字参数；`resume_query` 同步加参数，且 **`None` 时构造的
`Command` 与现状完全一致**（不带 `update=`），既有 HITL 测试一字未改仍绿。

**D4 与等时圈的联动零额外代码——这是本卡的亮点，也是集成测试要钉住的。**
chip 改 `iso_minutes=20` → `spec.iso_minutes=20` → 卡 5 的「显式时间预算才反哺检索」判据
（`_iso_request` 只看有无值，不看来源）自动成立：candidates 阶段先算 20 min 可达面，
再把 `polygon_wkt` 喂进检索、圆约束让位。约束来源从「意图槽位」扩到「槽位 ∪ 点改」，
下游一行没改——这正是 §2.2 把 spec 作为唯一约束载体的收益。

**D5 前端只采集原值，不裁决（§9.6）。** 点改控件把输入原样塞进 `changes`，
连 `type=number` 的 `min/max` 都不设——设了就是前端在裁决合法性，会出现「前端拦得住、
后端也拦得住」的两份口径。非法值发出去，422 由后端给，界面显示后端原文。

**D6 前端交互从简（§9.1 最小投入）。** chip 原地变控件，无弹层、无组件库：
`radius_m`/`iso_minutes` → `type=number`；`min_rating` → `step=0.5`；
`travel_mode` → 两态直接切换（点一下就在「步行 ⇄ 驾车」间互换并立即提交，没有第三种取值）。
Enter 提交、Esc / 失焦取消。不可点改的 chip（中心/类目/时段/关键词）保持 `<span>`。

**D7 chips 刷新以后端回读为准。** `editConstraint` 先 `applyResult`（候选/决策/地图/镜头全刷新），
再 `GET /api/sessions/{sid}` 取 `graph_state.spec` 覆盖 `store.constraints`——chips 显示的
永远是**图里真正生效**的那组约束，不是前端回显。SSE `constraints.updated` 本已带同一份载荷，
回读是权威收口（一次额外 GET，演示链路可接受）。

## 7. 风险

| 项 | 处置 |
|---|---|
| 重跑一轮会不会把上一轮的 `isochrone` 复用成旧圈 | 卡 5 的去重判据比 `mode/minutes/center` 三元组：chip 改了 minutes 或 mode 必然不匹配 → 重算；只有「改 radius、时间预算没变」才复用，复用是正确行为 |
| 422 之后状态真的不变吗 | 校验在 `run_query` 之前，图一次都没被 invoke；测试用 `GET /sessions/{sid}` 前后对比**整份 `graph_state` 的 JSON**（逐字符）钉死 |
| 前端 `Number("")` → 0 会被当合法值发出去 | `type=number` 清空后 v-model 是空串，提交前只判「能不能成数」，不能成数就取消编辑（这是「没有可发送的值」，不是合法性裁决） |
| 架构 §9.8 的 curl 示例是扁平 payload（`{"rent":80000}`） | 本卡按任务卡采用 `{"changes":…,"query":…}`：重跑必须有原文 query，扁平形态给不出。示例里的 `rent` 也不在四项白名单（spec 里没有租金键），已作为「陌生键必拒」的一条用例钉住（§8.1）；§9.8 原文不动 |
| chip 点改会不会渗到下一次新提问 | 实测渗到过（LangGraph 通道跨轮常驻，改过的 `半径 3000m` 顶掉了新一轮意图装配的 1500）→ 与 `gesture` 同规约：`run_query` **每轮都写**这个通道，不传即 `None`；补一条「新提问不继承点改」的用例 |

### 8.3 与既有契约的接缝（本次核对无误）

- §9.3 的 `FeedbackEvent` 与 `client.feedback()` 一字未改（`constraint_edit` 早在枚举里）；SSE 未新增事件类型，重跑走 `message.start → … → message.end`（与 draw_polygon 同款）。
- §5.6 冻结项零改动：7 节点与边、`IntentResult`、QueryBuilder 编译管线、SkillRegistry 协议都没碰；新增的是 `BrainState` 一个键 + 节点体内一段三路交集赋值。
- 铁律 2/3 复核：前端不算几何、不判约束合法性（连 `min/max` 都不设）；图内没有新 SQL、没有新坐标运算。
- 实测修掉的两处自身缺陷（都由用例先红后绿）：`radius_m` 取 float 会让「改回 1500」变 `1500.0` 而破坏逐字节一致 → 取 int（与意图槽位同型）；`v-model` 在 `type=number` 上自动转 number，`draft.value.trim()` 直接崩 → 控件值按 `string | number` 双形态收。
