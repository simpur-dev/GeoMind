# GeoMind 项目调研报告：优秀案例与技术选型

> 项目：2026 OceanBase 数据库大赛 · 高德赛道（方向「AI+数据库应用开发」）
> 汇编日期：2026-10-15。本文由四份调研底稿（research/01–04）汇编、去重、统一口径而成，未改动底稿原文。
> 核心命题：以 OceanBase 为多模检索底座（空间 + 标量 + 向量三模混合），叠加 Agent 编排层与「持续更新的结构化空间状态」闭环，构建空间智能体。

## 0. 调研概览

**调研目的**：为 GeoMind 的架构设计、技术选型与差异化叙事提供可追溯的案例参照，回答三个问题——(1) 学术上 LLM+GIS 智能体长什么样、规划模式与状态机制如何；(2) 工业界（高德/Mapbox/Google/OceanBase 官方）已把哪些空间能力 MCP 化、各自把空间计算放在哪一层；(3) OceanBase MySQL 模式的空间/向量能力到底能不能支撑「一条 SQL 三模混合」。

**来源数量统计**：共汇编来源 **60+ 条**，其中：学术论文/GitHub 约 21 条；工业产品官方文档约 12 条；Agent 框架与协议官方文档约 9 条；OceanBase 官方文档/教程/仓库约 20 条。覆盖学术案例 9 个（含 2 个「未找到同名项目」的如实标注）、工业案例 5 个、工程框架 5 组。

**标注规则**：
- 【已查证】= 底稿调研时已实际打开官方页面/论文摘要页/GitHub 核实；
- 【待实测/推测】= 官方文档无明确说法、需在赛题环境验证，或属工程经验/约定俗成；
- 链接一律保持调研时记录的原始 URL，不改写、不编造。

**口径统一说明**（四份底稿冲突处的裁决）：
1. 高德「四大 Skill」= 客流洞察、人群分析、智能选址、门店运营；「四种交付形态」= AI 云工作台、Agent 行业智能体、Skill/MCP Server、标准 API——以高德官方 PDF 精读（04）为准。
2. OceanBase 赛题为 **MySQL 模式**，空间列用标准类型 `POINT / LINESTRING / POLYGON / GEOMETRY`；底稿 01/02 中出现的 `SDO_GEOMETRY` 是 Oracle 模式类型，本文统一更正为 MySQL 模式类型（Oracle 模式仅作对照提及）。
3. 距离圈选：球面距离用 `ST_Distance_Sphere`（仅 Point 间、返回米）；距离谓词用 OB 私有 `_ST_Dwithin`（单位随坐标系，经纬度下是「度」需换算）；`ST_Union_Agg` 官方文档未见，待实测。
4. 向量 ANN 三要素：`ORDER BY 距离函数(...) APPROXIMATE LIMIT k`；混合查询官方语义为「HNSW 先召回，WHERE（含空间谓词）后过滤」。
5. 技术选型结论：**LangGraph 固定状态图 + 局部 ReAct 混合 + MCP Streamable HTTP**；不引入 AutoGen/CrewAI 做主架构。

## 1. 学术空间智能体与 LLM+GIS 案例

统一模板：名称/机构/时间/链接 → 架构摘要 → 可借鉴点 → 不足/局限 → 对 GeoMind 的启发。

### 1.1 MapAgent（重点参考，与 GeoMind 最对位）

- **名称/机构/时间**：MapAgent: A Hierarchical Agent for Geospatial Reasoning with Dynamic Map Tool Integration，BUET / Monash / QCRI 团队，2025-09。
- **链接**：https://arxiv.org/abs/2509.05933 ；开源 https://github.com/Hasebul/MapAgent 【已查证】
- **架构摘要**：两层脚手架——顶层 **Planner** 把用户查询分解为结构化子目标序列，依据一份 **Module Inventory（模块清单）** 为每个子目标选模块；底层 **Execution** 层含轻量模块与专属 Map-Service 模块（由 Map-Tool Agent 管理）。地图能力被聚合为 4 个高层异构工具：**Nearby（周边 POI）、PlaceInfo（地点详情）、Route（两点路径/距离/时间）、Trip（多点行程）**，每个由一个或多个 Google Maps 原生 API 封装，支持并行+串行混合编排。另有 Visual Place Recognizer（地图截图→中心地点与半径）、Sequencer、Solution Generator、Answer Generator（专门做一致性校验）。规划模式为 Plan-and-Execute 分层解耦；模块即插件、按清单注册。消融实验：去掉分层架构准确率掉 27.18%，再去掉自研地图工具再掉 22%。【已查证】
- **可借鉴点**：
  1. 模块清单 + 计划/执行解耦——Planner 只做「子目标→Skill」路由，不直接调底层 API；
  2. 把相近 API 聚合成 4 个高层工具，而非暴露扁平原始接口，避免工具爆炸；
  3. 独立的 Answer Generator 做一致性校验（对应 self-verifying）；
  4. 多模态入口（地图截图识别）。
- **不足/局限**：依赖 Google Maps API，空间计算在 API 侧，无数据库/空间索引概念；状态以中间消息传递，未沉淀为持久结构化空间状态。
- **对 GeoMind 的启发**：直接对位——采用「Planner（意图+约束）→ Skill 注册表（插件化）→ 空间计算下推 OceanBase + 高德 API」分层；并把三模混合检索封装为 Nearby（空间）/Attribute（标量）/Semantic（向量）三个可组合 Skill。

### 1.2 GeoGPT

- **名称/机构/时间**：GeoGPT: Understanding and Processing Geospatial Tasks through An Autonomous GPT，国内高校 GIS 团队，2023-07。
- **链接**：https://arxiv.org/abs/2307.07930 【已查证】
- **架构摘要**：以 LLM（gpt-3.5-turbo，temperature=0）为大脑，基于 LangChain 把成熟 GIS 工具串联，按自然语言自主完成「数据采集→处理→分析→出图」；思维链式 think-plan-execute，典型链路为 Buffer 选址→Intersect/Erase 叠加分析。属 AutoGPT 式类 ReAct 自主循环；空间计算下沉到专业工具，不进 LLM。【已查证】
- **可借鉴点**：①「基座大模型 + 专业空间工具」分工；②选址=Buffer→叠加→筛选多步空间算子串联，可直接映射为 OGC 函数下推；③temperature=0 + 固定工具集保证可复现、可审计。
- **不足/局限**：案例少、无系统 benchmark；无向量检索、无三模混合概念；无持久结构化空间状态。
- **对 GeoMind 的启发**：选址不是在 Python 里拼 GeoPandas，而是生成一条带 OGC 函数下推的 SQL，中间空间状态（候选区几何）以 MySQL 模式 `GEOMETRY` 列沉淀于 OceanBase，形成持续更新的结构化空间状态。

### 1.3 AutoGIS / LLM-Geo

- **名称/机构/时间**：Autonomous GIS: the next-generation AI-powered GIS，Zhenlong Li / Huan Ning（Penn State GIBD 实验室），2023-05；原型系统 **LLM-Geo**（GPT-4 + Python 环境）。
- **链接**：https://arxiv.org/abs/2305.06453 ；机构主页 https://giscience.psu.edu/llm-geo-an-open-source-autonomous-gis-prototype/ 【已查证】
- **架构摘要**：LLM 为推理核心，利用代码生成能力自动完成空间数据采集/分析/可视化；提出自主 GIS **五个自治目标**：self-generating / self-organizing / self-verifying / self-executing / self-growing。规划模式为 Plan-and-Execute + 代码生成执行（LLM 写 Python/Geo 代码再跑）。【已查证】
- **可借鉴点**：①五个自治目标可作 Agent 能力清单对标，尤其 self-verifying；②LLM 生成「可执行工作流」而非直接给答案，工作流即产物、可审计。
- **不足/局限**：原型早期，无日志、无代码沙箱测试；空间计算在 Python 进程内，未利用数据库内核/空间索引，大数据量不可扩展。
- **对 GeoMind 的启发**：把「代码生成执行」升级为「SQL/OGC 下推生成执行」——LLM 不写 GeoPandas 脚本，而生成命中空间索引、空间连接/聚合下推的 SQL，保留自执行范式又获得数据库级性能。

### 1.4 UrbanGPT（KDD 2024）

- **名称/机构/时间**：UrbanGPT: Spatio-Temporal Large Language Models，香港大学数据智能组，**KDD 2024 Full Paper**。
- **链接**：https://arxiv.org/abs/2403.00813 ；代码 https://github.com/HKUDS/UrbanGPT ；ACM https://dl.acm.org/doi/abs/10.1145/3637528.3671578 【已查证】
- **架构摘要**：不是工具调用 Agent，而是把**时空依赖编码器**与 LLM 指令微调结合，让 LLM 理解跨时间/跨空间依赖，做零样本时空预测（交通、人口流动、犯罪）。空间相关性被编码进表征层再喂 LLM。【已查证】
- **可借鉴点**：①城市要素≠单点 POI，而是带时空依赖的动态实体，客流/可达性分析要保留时间维；②标注稀缺时用结构化指令把意图翻译成可执行算子。
- **不足/局限**：面向预测而非交互式检索/选址，无工具调用、无数据库下推；需训练微调，工程门槛高。
- **对 GeoMind 的启发**：把时空依赖显式建模进结构化空间状态（POI 营业时间、客流时段字段），使三模混合检索可同时约束空间范围 + 时间窗 + 标量条件。

### 1.5 MapGPT（学术版，同名甄别）

> 同名甄别：另有 MapGPT-VLN（机器人视觉语言导航，arXiv 2401.07314，已排除）与 Mapbox MapGPT（商业产品），本文采纳空间数据方向的学术版。
- **名称/机构/时间**：Core Building Blocks: Next Gen Geo Spatial GPT Application（自称 MapGPT），2023-10。
- **链接**：https://arxiv.org/abs/2310.11029 【已查证】
- **架构摘要**：愿景型 building-blocks 短文：在空间+文本数据上构建 LLM，提出**面向空间信息的专用 tokenization 与向量表示（spatial vector representations）**，自然语言→空间计算→可视化端到端闭环。【已查证】
- **可借鉴点**：①显式的「空间向量表示」意识，与 POI 语义向量化直接相关；②端到端可视化闭环主张。
- **不足/局限**：仅 2 页体量，无系统实现与 benchmark；空间向量如何与关系/空间查询融合未落地。
- **对 GeoMind 的启发**：把「空间向量」作为一等公民——OceanBase 同库存 `GEOMETRY`（空间）+ 标量属性 + POI 语义向量，三模混合检索正是这一愿景的数据库级实现。

### 1.6 TP-RAG / EvoRAG（EMNLP 2025）

- **名称/机构/时间**：TP-RAG: Benchmarking Retrieval-Augmented LLM Agents for Spatiotemporal-Aware Travel Planning，**EMNLP 2025 Main**，2025-04。（注：TripGenie 是 Trip.com 商用 App 内 AI 助手，非学术 benchmark，仅作背景。）
- **链接**：https://arxiv.org/abs/2504.08694 ；DOI https://doi.org/10.18653/v1/2025.emnlp-main.626 ；TripGenie https://www.trip.com/newsroom/introducing-tripgenie-groundbreaking-ai-travel-assistant/ 【已查证】
- **架构摘要**：首个「检索增强 + 时空感知」旅游规划 benchmark：2,348 条真实查询、85,575 个标注 POI、18,784 条旅行轨迹；提出 EvoRAG 进化式框架，把检索轨迹与 LLM 推理协同。关键发现：参考轨迹显著提升路线效率，但检索并非总是有益——参考冲突/噪声下有约 12.59% 的失败差距。【已查证】
- **可借鉴点**：①POI + 高质量轨迹可做成向量库做检索增强；②「检索不一定有益、需去冲突」——多模结果要由规则/LLM 做一致性校验，而非无脑拼接。
- **不足/局限**：是 benchmark + 方法对比，不提供可复用运行时；检索源为游记文本，非结构化数据库空间查询。
- **对 GeoMind 的启发**：三模混合检索结果要过「时空合理性校验」（选出 POI 是否落在同一可达范围、时间是否冲突），对应高德 7 步闭环的「建立约束→生成候选→空间计算→数据决策」。

### 1.7 DynamicRouteGPT

- **名称/机构/时间**：Ziai Zhou, Bin Zhou, Hao Liu，2024-08。（注：未检索到恰好名为「RouteGPT」的独立论文，以 DynamicRouteGPT 为代表；相邻工作 PathGPT 见参考清单。）
- **链接**：https://arxiv.org/abs/2408.14185 【已查证】
- **架构摘要**：四模块——实时信息检索、备选路径生成、GPT 决策、动态路径调整。先用静态 Dijkstra 算全局最优基线，再在路口用 LLM（Llama3-8B）+ 马尔可夫链/贝叶斯做局部实时决策，并用因果图做反事实推理平衡全局最优与局部动态。规划模式为 Plan-and-Execute 变体：全局离线算路 + 局部 LLM 决策 + 动态调整闭环；LLM 不自己算最短路径，只做偏好/事件级选择。【已查证】
- **可借鉴点**：①**全局确定性算法 + 局部 LLM 决策**分层——复杂空间计算交成熟引擎，LLM 只处理自然语言偏好与异常事件；②实时信息检索作为独立模块（对应高德实时路况/POI 状态接入）。
- **不足/局限**：仅 v1 草稿；面向车载动态导航，不涉及 POI 三模检索与数据库下推。
- **对 GeoMind 的启发**：路径类需求不让 LLM「凭空算路」——高德路径规划 API 出候选 → OceanBase 做沿途 POI/可达性空间过滤 → LLM 按偏好（顺路/避开/评分）在候选中排序，形成「空间计算在引擎、偏好决策在 LLM」闭环。

### 1.8 CityGPT

- **名称/机构/时间**：CityGPT: Towards Urban IoT Learning, Analysis and Interaction with Multi-Agent System，2024-05。
- **链接**：https://arxiv.org/abs/2405.14691 【已查证】
- **架构摘要**：角色化多智能体——Requirement Agent 理解用户输入，把分析拆为 temporal 与 spatial 两条线，由 Temporal Agent / Spatial Agent 分别完成，再由时空融合/可视化 Agent 出图并生成文字描述。【已查证】
- **可借鉴点**：①空间分析与时间分析显式拆线再融合（可达性/客流热力正是时空联合问题）；②末端专门的「表达 Agent」负责地图可视化+文字解释。
- **不足/局限**：面向 IoT 时序数据，非 POI 检索/选址；无数据库空间下推。
- **对 GeoMind 的启发**：Agent 分工可按「空间算子 / 标量过滤 / 向量语义 / 地图表达」四条职责线拆分，最后由表达层合成地图 + 结构化结论。

### 1.9 GeoAgent

- **名称/机构/时间**：An LLM Agent for Automatic Geospatial Data Analysis（自称 GeoAgent），2024-10。
- **链接**：https://arxiv.org/abs/2410.18792 【已查证】
- **架构摘要**：把**代码解释器 + 静态分析 + RAG** 集成进**蒙特卡洛树搜索（MCTS）**，做地理数据多步程序生成，并贡献单轮/多轮任务 benchmark。核心结论：仅靠 LLM 自身知识不足以准确完成地理任务编程，需要连贯多步过程与多次函数调用。规划模式为 MCTS 搜索 + 执行反馈（试错-验证）。【已查证】
- **可借鉴点**：①**静态分析 + 执行反馈做自我校验**——生成的 SQL/工具调用先做语法/schema 校验再执行；②RAG 检索地理库/函数用法，缓解冷门函数幻觉（对应把 OceanBase 空间函数文档、高德 API schema 做 RAG）。
- **不足/局限**：空间计算仍在 Python 地理库进程内；MCTS 推理成本高，竞赛实时性需权衡。
- **对 GeoMind 的启发**：LLM 生成 SQL 后，先用 schema/函数合法性做静态校验、再用小样本 dry-run 验证命中空间索引，避免把错误空间计算下推到生产库。

### 1.10 未找到同名项目：LlamaRoute 与 Space2Graph（如实说明）

- **LlamaRoute**：未检索到名为「LlamaRoute」的学术论文或开源项目（仅命中 LLM-as-Router、Ollama 路由优化、EMNLP'25 Findings 的 LLMAP 等名称相近工作）。参照 LLMAP（https://aclanthology.org/2025.findings-emnlp.416.pdf）：为规避 POI 过多导致 token 超限，按类型采样 10 个 POI 输入 LLM。**对 GeoMind 的启发**：POI 大集不能全量塞 prompt，先用数据库空间/标量条件下推粗筛，只把少量候选交 LLM 排序，避免 token 爆炸与幻觉。【未找到同名；LLMAP 已查证】
- **Space2Graph**：未检索到同名项目（仅命中时空知识图谱综述 arXiv 2512.16487、网格投影空间知识图谱、city2graph 等相邻工作）。**对 GeoMind 的启发**：候选 POI 间空间关系（邻接/可达/包含）不必每次重算，可在结构化空间状态里维护轻量「空间关系图」供多跳推理复用。【未找到同名；相邻方向标题/摘要已查证】

## 2. 工业界开放案例

### 2.1 高德地图 MCP Server（官方 + 社区两版）

- **链接**：官方快速接入 https://lbs.amap.com/api/mcp-server/gettingstarted ；更新日志 https://lbs.amap.com/api/mcp-server/changelog ；社区包 https://pypi.org/project/amap-mcp-server/ 【已查证】
- **架构摘要**：官方版把 LBS Web 服务封装为 MCP Server，覆盖地理/逆地理编码、IP 定位、天气、骑行/步行/驾车/公交路径规划、距离测量、关键字/周边/详情搜索等 12 大接口；传输支持 **Streamable HTTP（推荐）** 与 stdio，客户端为 Cursor/Claude/Cline 等任意 MCP Host。社区版 `amap-mcp-server`（Python≥3.10，MIT）工具粒度更细（maps_geo/maps_direction_*/maps_around_search 等），每个工具提供「经纬度版」和「地址版」双入参（地址版内部先 geocode），支持 stdio/SSE/streamable-http 三传输，环境变量 `AMAP_MAPS_API_KEY` 鉴权。【已查证】
- **可借鉴点**：①「地址版/坐标版双入参」让工具内部消化 geocoding，减少 LLM 多跳；②作为在线 LBS 能力组接入 GeoMind。
- **不足/局限**：只覆盖在线搜 POI/算路/地理编码，**不含空间计算下推数据库、不含客流/选址叠加分析**；是无状态工具集，无结构化空间状态、无多步闭环、无人机确认。
- **对 GeoMind 的启发**：高德 MCP 的空白正是差异化空间——GeoMind 用 OceanBase 补「空间计算下推 + 三模混合 + 状态闭环」；高德在线 LBS 作为另一组 MCP tool 与自有 OB 计算互补。

### 2.2 高德千舆 · 空间智能开放平台（四大 Skill / 四交付形态）

## 3. Agent 工程框架与编排范式

### 3.1 LangGraph（推荐主框架）

- **链接**：Checkpointers https://docs.langchain.com/oss/python/langgraph/checkpointers ；Persistence https://docs.langchain.com/oss/javascript/langgraph/persistence ；Subgraphs https://docs.langchain.com/oss/python/langgraph/use-subgraphs ；Interrupts/HITL https://docs.langchain.com/oss/javascript/langgraph/interrupts 【已查证】
- **机制要点**：StateGraph 把工作流建模为「共享状态对象 + 节点 + 边（含条件边）」；**Checkpointer** 每个 super-step 把图状态快照落盘、按 thread_id 组织线程，免费获得会话记忆/故障恢复/time-travel/HITL；**Store** 管跨线程长期数据（用户偏好、共享事实）；**interrupt()** 在任意节点暂停、人工检视后 `Command(resume=...)` 恢复；**Subgraph** 分 per-invocation 与 per-thread 两模式；支持 token/节点多粒度流式。【已查证】
- **优点**：原生覆盖「持久化结构化空间状态 + 用户改动触发局部重算 + 7 步闭环 + HITL」。
- **局限**：是低级编排层，需自己组装状态 schema 与节点；学习曲线比 Dify 陡。
- **对 GeoMind 的用法**：结构化空间状态 = TypedDict/Pydantic 共享状态（候选集 GeoJSON、约束、当前 bbox、过滤条件、已确认项、脏标记），checkpointer 按 thread 持久化；「用户每次修改触发局部重算」= 状态变更后条件边只重算受影响节点；7 步闭环 = 一条主 StateGraph，HITL interrupt 落在「生成候选后请用户确认/改约束」；选址/可达性/客流分析做成可复用子图。

### 3.2 MCP（Model Context Protocol）——空间能力插件化的事实标准

- **链接**：Architecture https://modelcontextprotocol.io/docs/learn/architecture ；Transports（2025-11-25 规范）https://modelcontextprotocol.io/specification/2025-11-25/basic/transports ；2026-07-28 RC 公告 https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/ 【已查证】
- **机制要点**：Host↔Server 基于 JSON-RPC 2.0；**三原语** = Tools（`tools/list` 动态发现 + `tools/call`）、Resources（URI 寻址上下文数据）、Prompts（可复用模板），客户端侧另有 Sampling/Elicitation/Logging；**传输** = stdio（本地子进程）与 **Streamable HTTP**（远程，HTTP POST + 可选 SSE，支持 bearer/OAuth），旧独立 SSE 已并入 Streamable HTTP；2026-07 RC 引入无状态核心、Extensions、Tasks（耐久执行）、**MCP Apps（富 UI 面板，Mapbox render_map_tool 即用此）**。【已查证】
- **优点**：动态发现 + JSON Schema 入参——新增一个空间算子只需注册新 tool、不动主图；tool 返回 content 数组支持 text/image/结构化，GeoJSON 可直交前端；远程 Streamable HTTP 便于评测替换；Elicitation 对应 7 步「用户反馈」。
- **局限**：规范本身没有强制的「Skill」一等概念——业界/Skill 市场里的 Skill 通常是「一组相关 MCP Tool + Prompt + 说明文档」的打包约定（【约定，非规范原文】）。
- **对 GeoMind 的用法**：把 OceanBase 空间能力封装为独立 MCP Server（Streamable HTTP），分三层——①原子空间算子（ST_Buffer/ST_Contains/ST_Distance_Sphere/ST_Union/ST_Area/ST_Centroid，走空间索引）；②POI 三模混合检索（向量+标量+空间，pyobvector）；③业务 Skill 子图（智能选址、等时圈可达性、客流热力）。新增赛题能力 = 注册新 MCP tool。

### 3.3 AutoGen（微软）与 CrewAI —— 多智能体取舍

- **链接**：框架对比 https://learnwithparam.com/blog/choosing-ai-agent-framework-langgraph-llamaindex-crewai-autogen ；编排平台选型 https://www.1raft.com/blog/ai-orchestration-platform-guide 【已查证】
- **机制要点**：CrewAI 以「角色+任务+Crew」建模团队流水线；AutoGen 以「可对话 Agent + 显式 handoff」建模自由对话/辩论。业界共识：多智能体只在三种情况划算——单上下文装不下需分发、需要并行执行、需要多套专精人格互相校验；单 LLM + 几个工具的线性/分支流程，单智能体 + 状态图更简单可控、更省 token。【已查证】
- **对 GeoMind 的取舍**：核心是确定性空间计算/SQL，步骤强依赖共享结构化状态，不是「多专家辩论」——**不采用 AutoGen/CrewAI 做主架构**。后期若要「一个 Agent 出选址方案 + 一个反方挑错」，用 LangGraph 双节点或 handoff 子图实现即可。

### 3.4 Plan-and-Execute vs ReAct（混合策略结论）

- **链接**：LangChain 官方博客 https://www.blog.langchain.com/planning-agents/ ；2026 对比 https://www.agentnative.dev/compare/react-vs-plan-and-execute-for-agent-loops 【已查证】
- **机制要点**：ReAct = Thinking→Acting→Observing 交错，灵活但长任务上下文膨胀、易推理漂移；Plan-and-Execute = Planner 一次性出多步计划、Executor 逐步执行、Replanner 决定结束/继续/改计划，编译后计划比纯 ReAct 省 3–5× token、计划本身可审计、步骤可并行。【已查证】
- **对 GeoMind 的结论（混合）**：空间计算/SQL 是确定性、可预测、可审计的，不适合纯 ReAct 每步重决策。**外层用 StateGraph 把 7 步固化为有向流程**（≈Plan-and-Execute 的「计划」由图结构承担，可审计不漂移）；**只在「理解用户意图 / 消歧 / 决定是否重规划」两个节点用 ReAct 式 LLM 调用**；空间计算节点是纯确定性 SQL 下推、不调 LLM。

### 3.5 LlamaIndex 与 Dify 的角色（补充）

- **LlamaIndex**（OB 集成 https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004481735 ）：定位 data/RAG-first（Query Engine/Retriever/索引抽象）。**用法**：当「检索/嵌入/三模召回」工具库用（尤其召回阶段），不用它做长会话、结构化状态、HITL 工作流编排——那是 LangGraph 的职责。
- **Dify**：低代码 Agent 平台，适合快速搭 demo/答辩演示壳；但对「结构化空间状态 + 局部重算 + SQL 下推精细控制」掌控力弱于 LangGraph，正式参赛主代码建议 Python + FastAPI + LangGraph 自托管。

## 4. OceanBase 空间与多模能力核实（结论速查）

> 范围：4.x、**MySQL 模式**（赛题模式）；Oracle 模式仅对照。来源均为官方文档逐条核实（见第 6 节）。

**空间类型与 SRID【已查证】**：8 种标准类型 `GEOMETRY / POINT / LINESTRING / POLYGON / MULTIPOINT / MULTILINESTRING / MULTIPOLYGON / GEOMETRYCOLLECTION`；列级声明 `NOT NULL SRID 4326`（高德经纬度即 WGS84，直接匹配）；定义 SRID 后插入其他 SRID 几何报错，未定义 SRID 的列优化器不会选空间索引。部署后需 `import_srs_data.py` 导入约 5152 条 SRS 记录（赛题环境若已内置可跳过）。输入输出：`ST_GeomFromText(wkt[,srid])`、`ST_AsText`、`ST_AsGeoJSON`（V4.3.1 起）；`ST_AsBinary` 【待实测】。

**空间函数分类清单**：

| 类别 | 已查证函数 | 待实测/未见 |
|---|---|---|
| 关系判断 | ST_Intersects, ST_Contains, ST_Within, ST_Distance, ST_Distance_Sphere（球面最短距离，单位米，仅 Point/MultiPoint）, ST_IsValid, ST_Crosses, ST_Overlaps, 私有 `_ST_Dwithin`（距离圈选，单位随坐标系，经纬度下是「度」需换算）, `_ST_Covers`, `_ST_Touches`, `_ST_Equals` | SDO_Within_Distance（Oracle 风格，不适用） |
| 几何属性 | ST_Area, ST_SRID, ST_X/ST_Y, ST_Longitude/ST_Latitude, 私有 `_ST_SetSRID` | — |
| 几何运算 | ST_Buffer(+ST_Buffer_Strategy), ST_Transform, ST_Difference, ST_Union（二元）, ST_SymDifference, ST_Length, ST_Centroid, 私有 `_ST_Buffer/_ST_Transform/_ST_ClipByBox2D/_ST_MakeEnvelope`, ST_AsMVTGeom | **ST_Union_Agg（空间聚合）官方未见，待实测**；ST_Intersection 独立函数未单列，待实测；MBR* 函数族按 MySQL 兼容推断存在、未逐字核实 |
| 空间连接 | 无专门算子；常规 `JOIN ... ON ST_Contains(...) / _ST_Dwithin(...)`，Nested Loop Join 支持任意连接条件 | 是否有空间感知 join 优化（索引嵌套循环+MBR 预筛）官方未说明，需 EXPLAIN 实测 |

**空间索引【已查证】**：`CREATE SPATIAL INDEX idx ON t(g)`；关键限制——仅局部索引不支持全局索引；索引列必须 `NOT NULL` 且必须定义 SRID（否则查询时不生效）；只能建在空间类型列；**索引内部存储几何 MBR（最小外接矩形）做粗筛**，官方文档未出现「R-Tree」字样【MBR 索引已查证；是否严格 R-Tree 待实测，MySQL 系通常是 R-Tree】。精确形状计算仍是算子内计算，索引只做 MBR 粗筛。

**向量类型与 HNSW【已查证】**：`embedding VECTOR(<dim>)`，建列必须指定维度；单精度浮点、不允许 NaN/Inf；存储最大 16000 维。版本演进：V4.3.3 MySQL 模式首发（实验特性，HNSW 最大 2000 维，距离仅 L2/inner_product）；**V4.4.0 HNSW 最大 4096 维，新增 HNSW_SQ/HNSW_BQ/IVF_flat/IVF_PQ，距离新增 cosine，明确支持「标量条件 + 空间关系（ST_Intersects 等）」作向量查询过滤**；V4.4.1 向量搜索默认启用；V4.5.0 HNSW 参数文档化。建索引 DDL：`VECTOR INDEX ... WITH (distance=cosine, type=hnsw, lib=vsag, m=16, ef_construction=200, ef_search=64)`；HNSW 系为内存索引需完整载入内存；索引名长度软限制（HNSW ≤25 字符）。

**ANN 语法三要素【已查证】**：`ORDER BY cosine_distance(embedding, '[...]') APPROXIMATE LIMIT k`——①必须带 `APPROXIMATE/APPROX`（不带则不走向量索引、也不报错，退化为全表精确计算）；②必须有 ORDER BY + LIMIT，ORDER BY 只支持单个向量条件，`LIMIT+OFFSET ∈ (0,16384]`；③距离函数名 `l2_distance / cosine_distance / negative_inner_product` 必须与索引 distance 匹配；无 PG 的 `<=>` 算子。

**混合查询官方语义与两种执行策略【已查证机制；工程调优为经验】**：官方原文——「过滤条件可以是标量条件，**可以是空间关系（如 ST_Intersects）**」「`WHERE` 条件会作为向量索引搜索**后的过滤条件**」。即一条 SQL 内「向量 ANN（APPROXIMATE LIMIT K）+ WHERE 标量 + WHERE 空间谓词」官方支持，语义是 **HNSW 先召回 → WHERE（含空间谓词）后过滤**。两种执行策略：
1. **一条 SQL 后过滤**（官方语义）：写法如上；风险是过滤很强时 APPROXIMATE LIMIT 10 召回后过滤可能不足 10 条甚至为 0——工程上放大 LIMIT（先召回 50~100 条再过滤截断展示）【工程经验，非官方明文】；
2. **先空间粗筛再向量精排**：先用空间谓词/标量条件在 OB 侧粗筛出候选集，再在候选上做向量排序——更可控，但需实测优化器是否真能双索引并行（官方未承诺，必须 EXPLAIN）。

**与 PostGIS 对比【已查证】**：OB 用 MySQL GIS 语法族 + PG 兼容 `_ST_*` 私有函数组；函数完备度不及 PostGIS（无 ST_Union_Agg 类聚合、无栅格/routing）；但**同库同时有 SPATIAL INDEX + VECTOR INDEX(HNSW) + 全文索引 + 标量索引、一条 SQL 三模混合**是 PostGIS（需 pgvector 扩展拼配）不具备的。结论：GeoMind 不追求 PostGIS 全套函数，主打 OB 独有「单库三模混合」叙事。

**文旅教程摘要**：见 2.5——一行景点记录同时含标量+POINT(SRID 4326)+VECTOR(BGE-m3 1024 维)，混合查询走「空间过滤 + 语义向量召回 + LLM 生成推荐」；高德 API 仅用基础 LBS（地理/逆地理编码），未涉及路径规划。社区版 `oceanbase/oceanbase-ce` 可跑，seekdb 为精简版。【已查证；完整建表 DDL 与混合 SQL 原文在仓库 `src/` 内，需 clone 精读】

### 5.3 十条综合结论

1. **确定性空间计算必须工具化并下推数据库内核。** 依据：GeoGPT/AutoGIS 的 LLM 编排+专业计算分工、Mapbox Turf.js 本地算子层、高德 PDF「不让模型猜距离」铁律；GeoMind 把同构算子落到 OceanBase `ST_*` + MBR 空间索引，而非 Python 进程或 API 侧。
2. **状态图 + 结构化空间状态是长会话闭环的标配。** 依据：高德 PDF「持续更新的结构化空间状态」、LangGraph StateGraph/checkpointer/interrupt；GeoMind 以 Pydantic Typed State 承载候选集/约束/脏标记，条件边实现局部重算。
3. **Skill 要分原子层与场景层。** 依据：MapAgent 的 4 个聚合工具、高德四大原子 Skill、Mapbox 四层工具；GeoMind = MCP 原子算子层（ST_*）+ 三模检索层 + 业务 Skill 子图层（选址/可达性/客流）。
4. **地图渲染应声明式（回 GeoJSON 富面板）。** 依据：Mapbox render_map_tool、高德 Loca、Google place_id 上图；GeoMind 地图节点回 GeoJSON 交前端高德 JS API/Loca，而非文字卡片堆砌。
5. **SQL 生成要静态校验 + dry-run。** 依据：GeoAgent 的静态分析+执行反馈、AutoGIS self-verifying；GeoMind 生成 SQL 先过 schema/函数合法性校验，再小样本 dry-run 验证命中索引。
6. **规划模式用「固定状态图骨架 + 局部 ReAct」混合，不做多智能体辩论。** 依据：Plan-and-Execute 比纯 ReAct 省 3–5× token、MapAgent 计划/执行解耦、多智能体取舍共识；GeoMind 仅意图理解/消歧节点调 LLM，空间计算节点纯确定性。
7. **POI 大集先粗筛后精排，避免 token 爆炸。** 依据：LLMAP 采样 10 个 POI、TP-RAG 检索噪声教训；GeoMind 先用 OB 空间+标量条件下推粗筛，少量候选交 LLM 按语义向量/偏好排序。
8. **三模混合检索要过「时空合理性校验」。** 依据：TP-RAG 约 12.59% 检索失败差距、UrbanGPT 时间维；GeoMind 在数据决策步校验候选是否同可达范围、时间是否冲突。
9. **混合查询按官方「HNSW 召回 → WHERE 后过滤」语义写 SQL，并放大 LIMIT、EXPLAIN 实测双索引。** 依据：OceanBase 4.4.0 官方原文；`ST_Union_Agg`/双索引并行/MBR 函数族均待赛题环境实测。
10. **差异化叙事 = Mapbox 把算子放应用层，GeoMind 把同构算子下推 OB 内核 + 三模混合 + 结构化状态闭环。** 依据：5.2 工业界空位分析——未发现公开案例把「空间计算下推数据库内核 + MCP Skill + 结构化空间状态闭环」三者打通，这正是 GeoMind 的创新空位与赛题评分点。
